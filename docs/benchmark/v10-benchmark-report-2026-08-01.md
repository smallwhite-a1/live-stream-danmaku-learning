# V10 压测实测报告

测试日期：2026-08-01

本次测试使用 Apple Silicon Mac，8 核 CPU、16 GB 内存、macOS 15.6.1。结果只代表本机环境，不作为线上容量承诺。

## 测试组件

- V10 WebSocket 服务
- JMeter 5.6.3 + WebSocket Samplers 1.3.2
- Redis 7
- Apache Kafka 3.7.2 单节点 KRaft
- MySQL 8.0
- V10 消费者

原始结果保存在 `results/2026-08-01-v10-*`。

## 关键观察

### 1. WebSocket 广播

500 个连接的测试没有出现 `ingress_dropped`、`dropped_jobs`、`dropped_messages` 或慢客户端断开。服务进程在测试期间最高观察到约 60% CPU，占用量会受到 Go benchmark 客户端和服务端同时运行的影响。

这只能说明本机在该测试规模下没有触发服务端保护阈值，不能推导出线上连接容量。

### 2. Redis 跨实例和熔断

两个服务共享 Redis，两个房间视角都收到了两台服务产生的全部消息。停止 Redis 后，实时广播仍然继续，服务端记录：

- Redis 发布错误：6
- 熔断降级：30
- 熔断打开：1
- 本地降级广播：36
- 广播丢弃：0

Redis 恢复后，恢复探针成功 1 次，熔断回到 closed。

### 3. Kafka 和 MySQL

小规模完整链路中，58 条弹幕全部完成：

```text
WebSocket 接收 58
Kafka 入队 58
Kafka 确认 58
MySQL 插入 58
```

高频场景中，业务接收 1652 条，但只有 1648 条进入 Kafka，4 条因为非阻塞发布队列满而被明确丢弃。当前设计优先保证实时广播，持久化链路在极端突发下是 best effort。

这说明 `/metrics` 中的 `kafka.status=healthy` 不能单独作为数据完整性的依据，必须同时看 `persist_dropped`、Kafka 确认数和 MySQL 最终数量。

### 4. 同批次重复消息修复

压测发现，相同 `message_id` 分到两个批次时，幂等插入正常；但两个相同 `message_id` 同时位于一个批次时，原实现将它们一起交给 MySQL 的批量 `INSERT ... ON DUPLICATE KEY`，MySQL 返回：

```text
Error 1869: Auto-increment value in UPDATE conflicts with internally generated values
```

消费者因此暂停分区并重试，后续消息会被阻塞。

修复方式是在消费者提交数据库前按 `message_id` 保留批次内第一次出现的记录，数据库唯一键仍作为跨批次重试的最后一道保障。Kafka offset 仍按原始批次全部提交，重复数量仍进入 `duplicates` 指标。

修复后的真实验证结果：

```text
Kafka 同批次输入：2 条，message_id 相同
Consumer：parsed=2 saved=2 inserted=1 duplicates=1 retries=0 failed_batches=0
MySQL：COUNT(*)=1，COUNT(DISTINCT message_id)=1
```

因此当前可以说明“批内和跨批次重复都不会导致重复落库或阻塞分区”，但仍应继续保留唯一索引和重复指标。

### 5. 与原作者 README 压测数据对比

根目录 README 的原作者数据为：6 万以上长连接、150 万下行 QPS、2.5 万上行 QPS、周期丢包率低于 1%、500 万条积压 2 分钟内落盘。本次 V10 数据没有达到这些数字，原因首先是测试目标和规模不同，并不能直接视为实现退化。

| 指标 | 原作者数据 | 本次本机结果 | 主要原因 |
| --- | ---: | ---: | --- |
| 长连接 | 6 万+ | 500 个连接 | 本次先做小规模安全验证；V10 默认连接上限 5000，本机未进行 6 万连接测试 |
| 下行广播 | 峰值 150 万 QPS | 500 连接约 7.4 万条/秒客户端接收 | 客户端规模约为原测试的 1/120；V10 本轮只启用 4 个广播 worker，原项目配置为 100 个 worker |
| 上行处理 | 2.5 万 QPS | 高频场景实际接收约 330 条/秒 | V10 默认启用用户 5 条/秒、房间 500 条/秒限流；本次 50 个客户端集中在一个房间，测试重点是治理而非裸吞吐 |
| 持久化 | 500 万条约 40k QPS | 小规模 58 条全部落库；突发场景 1648 条落库、4 条队列丢弃 | 本次 Kafka、MySQL 均为单节点 Docker；V10 仍采用非阻塞持久化队列，队列满时优先保证实时广播 |
| 丢包率 | 周期丢包率 < 1% | 500 连接广播队列丢弃 0；持久化突发明确丢弃 4 条 | 两者统计口径不同：原数据主要关注广播交付，本次同时暴露持久化分支的 best effort 丢弃 |

还存在测试工具差异：原项目的 benchmark 主要模拟大量长连接和单房间广播，V10 的 Go benchmark 同时统计限流、过载和错误；JMeter 本轮只验证连接、发送和读取采样，不能替代消息级广播覆盖率测试。

## 本轮 WebSocket 延迟百分位

2026-08-01 追加使用 JMeter 5.6.3 测试 V10 无中间件模式，500 个线程逐步建立连接，每个线程完成一次连接、发送和读取。共完成 1500 个采样，错误率 0%。

| 采样项 | 样本数 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: |
| 建立 WebSocket | 500 | 1 ms | 1 ms | 1 ms |
| 发送弹幕 | 500 | 0 ms | 0 ms | 1 ms |
| 读取房间广播 | 500 | 1 ms | 2 ms | 4 ms |

这里的“读取房间广播”是 JMeter 从已有连接读取一条消息所花的采样时间，不是严格的“发送端发出到其他客户端收到”的端到端延迟。由于当前协议没有把发送时间、服务端处理时间和接收时间关联起来，这组数据适合描述 WebSocket 采样延迟，不应直接写成完整链路 P99。服务端同时记录 `ingress_dropped=0`、`dropped_jobs=0`、`dropped_messages=0`。

## 本轮消息级端到端延迟

在 Go benchmark 中为压测消息写入客户端发送时间，服务端只在内存消息中转发该字段，MySQL 模型通过 `gorm:"-"` 忽略，不改变落库结构。100 个连接全部发送，平均间隔约 300ms，持续 10 秒：

```text
total_connected=100
sent=3187
received=317703
latency_samples=317703
latency_p50=868µs
latency_p95=2.958ms
latency_p99=4.841ms
rate_limited=0 overloaded=0 errors=0
```

这里的端到端延迟是同一台压测机上“客户端发出时间”到“任一房间客户端收到广播”的耗时，包含服务端接收、房间广播队列、工作池和 WebSocket 写出，不包含跨机器网络时延。它比 JMeter 的读取采样更接近业务体验，但仍不能代表线上跨机房延迟。

## 1000、2000、5000 连接阶梯压测

为观察连接规模增加后的容量变化，本轮关闭 Redis、Kafka 和 MySQL，服务端统一使用 16 个广播 worker，并将连接上限和单 IP 上限调为 6000。三档均保持约 100 个活跃发送端，平均发送间隔约 300ms，避免连接数增加时同时放大上行消息数量。

| 指标 | 1000 连接 | 2000 连接 | 5000 连接 |
| --- | ---: | ---: | ---: |
| 实际建立连接 | 1000 | 2000 | 4994 |
| 发送消息 | 4548 | 4610 | 4742 |
| 客户端接收广播 | 4,508,581 | 1,084,976 | 1,146,780 |
| P50 | 4.80ms | 187.10ms | 101.73ms |
| P95 | 22.64ms | 1.048s | 1.443s |
| P99 | 41.55ms | 1.791s | 2.211s |
| 过载响应 | 0 | 977 | 904 |
| 上行队列丢弃 | 0 | 3360 | 2849 |
| 下行广播丢弃 | 0 | 506,718 | 1,944,052 |
| 慢客户端断开 | 0 | 1724 | 4152 |
| 服务端 CPU 峰值 | 214.8% | 309.4% | 264.1% |
| 服务端内存峰值 | 约 55MB | 约 168MB | 约 291MB |

1000 连接档完成约 450.9 万次广播接收，P99 为 41.55ms，错误、过载和广播丢弃均为 0，属于本轮稳定负载点。按 15 秒配置窗口折算，客户端合计处理约 30 万次广播接收/秒。

2000 连接虽然全部建立，但连接就绪后多个采样秒的接收量降为 0，尾延迟进入秒级，并出现大量上行丢弃和慢客户端断开。这一档已经越过稳定容量边界。

5000 个目标连接中建立 4994 个，但最终出现 4152 个慢客户端断开和约 194 万次下行广播丢弃。其 P50 低于 2000 档并不代表性能恢复，而是大量失败样本没有进入延迟统计造成的幸存者偏差。测试配置时长为 18 秒，实际进程耗时 33.07 秒，也反映出过载后的清理成本。

因此，在本机、单进程、单房间、约 300 条/秒上行的负载模型下，可以得出的结论是：1000 连接稳定，容量拐点位于 1000 到 2000 连接之间；接近 5000 个套接字可以建立，但无法稳定承载全房间广播。完整参数和原始文件说明见 `results/2026-08-01-v10-staircase/README.md`。

## 当前限制

1. 当前端到端延迟采样由压测客户端保存，服务端 `/metrics` 尚未提供延迟直方图。
2. JMeter 的读取采样证明客户端能够收到一条广播，但没有完成每条消息对所有房间成员的覆盖率关联。
3. Consumer 和 MySQL 指标目前主要通过消费者日志和数据库查询获得，还没有统一的指标端点。
4. 原始 compose 使用的 `bitnami/kafka:3.7` 仍受到本机镜像代理 403 影响；本次使用 `apache/kafka:3.7.2` 临时完成验证，compose 文件本身尚未替换。
5. 服务端和压测客户端运行在同一台机器上，CPU、内存和网络栈相互竞争；本次测试没有运行分布式压测，也没有把本机结果外推到线上容量。

## 下一步优化优先级

1. 给 Kafka 发布队列明确配置数据策略：阻塞等待、持久化本地缓冲，或接受并统计丢弃。
2. 为消息增加压测批次标识，继续采集接入、广播、Kafka 确认和 MySQL 落库各阶段时间。
3. 为消费者增加可查询的指标端点，统一收集消费积压、批量耗时、重试和死信。
4. 在独立压测机上逐步提高连接数，并单独测试广播、上行、Kafka 落盘三条容量曲线。
