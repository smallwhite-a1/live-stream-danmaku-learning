# V12 AI 洞察：100-500 房间混合压测报告

## 范围与方法

本报告验证的是独立 `v11/insight` 模块的完整应用链路：

```text
生成弹幕 -> 内存时间窗口 -> 到期窗口分批领取 -> 16 个 worker
-> 模型并发闸门（最多 16）-> 模型结果校验/规则降级
-> 内存结果仓库 -> HTTP latest 查询核验
```

每个房间生成 4 条弹幕并形成 1 个到期窗口。处理器每次最多领取 32 个窗口，因此 500 房间会经历多次领取；所有结果均由并发 HTTP 请求逐房间校验。

`FakeModel` 的正常延迟为 5-20 ms；超时场景的保护超时缩短为 50 ms，目的是在本机快速验证取消、熔断和降级语义，不能把这组数值等同于线上 15 秒超时的耗时。

## 实测结果

统一配置：16 个 processor worker、16 个模型并发上限。P50/P95/P99 是 FakeModel 单次调用耗时，不是跨网络端到端延迟。

| 场景 | 房间 | 正常/降级/失败 | HTTP 核验 | 模型调用峰值并发 | P50/P95/P99 | 全链路耗时 |
| --- | ---: | --- | ---: | ---: | --- | --- |
| 正常 | 100 | 100/0/0 | 100 | 16 | 10.67/20.58/20.64 ms | 147.59 ms |
| 正常 | 300 | 300/0/0 | 300 | 16 | 10.67/20.57/20.62 ms | 372.76 ms |
| 正常 | 500 | 500/0/0 | 500 | 16 | 12.53/20.59/20.72 ms | 616.17 ms |
| 混合异常 | 100 | 89/11/0 | 100 | 16 | 15.02/20.58/51.02 ms | 192.73 ms |
| 混合异常 | 300 | 267/33/0 | 300 | 16 | 15.02/20.66/51.04 ms | 521.73 ms |
| 混合异常 | 500 | 445/55/0 | 500 | 16 | 15.02/20.66/51.04 ms | 845.36 ms |

混合异常按调用序号注入：约 5% 上游错误、4% 非法 JSON、约 3% 超时，部分故障会重叠，因此 500 房间最终有 55 条降级结果。

## 结论

1. 正常场景下，500 个到期窗口均得到一条正常结果，HTTP 核验 500/500；模型实际峰值并发未超过 16。
2. 所有异常场景下，`failed=0`，每一个窗口都产生可查询的规则降级结果，未出现静默丢窗。
3. 连续不可用或超时后，熔断会阻止大部分后续调用；因此 500 房间的实际 FakeModel 调用数远小于 500，系统快速转入规则兜底。

## 真实 DeepSeek 验证

实现新增了 OpenAI 兼容的 DeepSeek 适配器，默认模型为 `deepseek-v4-flash`，并完成了本地 HTTP 协议测试：鉴权头、JSON 模式、Token 解析和 429 分类均已验证。

真实供应商烟雾验证已完成。密钥由 macOS 钥匙串临时注入子进程，未打印、未写入仓库。使用 fixture 回放 4 个窗口后，历史接口结果如下：

| 房间 | 历史窗口数 | 正常 | 降级 | 模型 | 最新窗口模型耗时 |
| --- | ---: | ---: | ---: | --- | ---: |
| `room-alpha` | 2 | 2 | 0 | `deepseek-v4-flash` | 82 ms |
| `room-beta` | 2 | 2 | 0 | `deepseek-v4-flash` | 75 ms |

这证明真实调用、JSON 输出、证据校验、结果落库和 HTTP 查询链路可以闭环；它不是 500 房间真实模型压测。后续可通过以下命令复跑小流量验证：

```bash
DEEPSEEK_API_KEY=... go run ./v11/insight/cmd/insightd -model=deepseek -listen=127.0.0.1:18125
```

真实模型只建议使用 fixture 的 4 个窗口进行烟雾验证，观察 JSON、证据校验、Token 和实际调用耗时；不应用于 500 房间压测。

## 当前边界

- 该报告覆盖 V11 AI 洞察模块，不包含 V10 的 WebSocket、Redis、Kafka 和 MySQL 链路；后者应使用已有的 JMeter/WebSocket 压测单独报告。
- 已实现模型并发上限、调用超时与连续故障熔断；尚未实现按 RPS 平滑请求的令牌桶限流，接入真实模型前应补充。
- 结果仓库与窗口存储仍是内存实现，不能代表 MySQL、Redis 或 Kafka 的生产吞吐。

## 公开真实弹幕回放补充

数据来自已授权访问的 DanmakuTPP-Events 分片，仅使用文本和时间戳字段；原始分片与清洗结果都位于 Git 忽略的 `data/raw/`、`data/processed/`。清洗命令 `cmd/datasetclean` 去除空白、超长、无效 UTF-8、URL 和含 `@` 的文本，将 10 段源视频映射为 10 个逻辑房间，每房间均匀选取 500 条真实弹幕，生成共 5000 条 JSONL 事件。源数据未提供用户身份，因此本地 `user_id` 为不可逆匿名映射。

真实模型结果分两部分：单房间 500 条真实弹幕经 `deepseek-v4-flash` 处理为 `normal`；10 房间同时以 10 路 worker 调用时，结果为 `normal=0`、`degraded=10`、`failed=0`，10 个窗口均可查询。这说明当前兜底正确，但真实模型并发下的输出稳定性尚不足，不能把该场景描述为“10 房间真实模型分析全部成功”。后续应先完成分层采样、失败原因观测和一次结构修复，再复测。
