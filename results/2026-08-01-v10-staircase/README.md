# V10 WebSocket 阶梯压测

测试时间：2026-08-01

## 1. 测试目标

本轮测试验证单进程、单房间广播在 1000、2000、5000 个 WebSocket 连接下的稳定性，并同时观察：

- 消息级端到端 P50、P95、P99；
- 服务端过载、广播丢弃和慢客户端断开；
- 服务端 CPU 和内存峰值；
- “可以建立连接”与“可以稳定广播”的差别。

本轮关闭 Redis、Kafka 和 MySQL，只测 WebSocket 接入与房间广播。服务端和压测客户端运行在同一台 Apple Silicon Mac 上，共享 8 核 CPU 和 16 GB 内存，因此结果代表本机整套测试环境，不是独立服务器容量。

## 2. 测试参数

服务端统一参数：

```text
-redis=false
-kafka=false
-max-connections=6000
-max-connections-per-ip=6000
-workers=16
```

为保证三档测试的上行压力接近，均保持约 100 个活跃发送端，平均发送间隔约 300ms：

| 连接数 | 活跃发送比例 | 配置时长 | 启动间隔 |
| ---: | ---: | ---: | ---: |
| 1000 | 10% | 15s | 1ms |
| 2000 | 5% | 15s | 1ms |
| 5000 | 2% | 18s | 1ms |

## 3. 实测结果

| 指标 | 1000 连接 | 2000 连接 | 5000 连接 |
| --- | ---: | ---: | ---: |
| 实际建立连接 | 1000 | 2000 | 4994 |
| 发送消息 | 4548 | 4610 | 4742 |
| 客户端接收广播 | 4,508,581 | 1,084,976 | 1,146,780 |
| P50 | 4.80ms | 187.10ms | 101.73ms |
| P95 | 22.64ms | 1.048s | 1.443s |
| P99 | 41.55ms | 1.791s | 2.211s |
| 过载响应 | 0 | 977 | 904 |
| 客户端错误 | 0 | 0 | 6 |
| 上行队列丢弃 | 0 | 3360 | 2849 |
| 下行广播丢弃 | 0 | 506,718 | 1,944,052 |
| 慢客户端断开 | 0 | 1724 | 4152 |
| 服务端 CPU 峰值 | 214.8% | 309.4% | 264.1% |
| 服务端内存峰值 | 约 55MB | 约 168MB | 约 291MB |

CPU 百分比按 macOS 进程口径记录，100% 约等于占满一个逻辑核。2000 连接的下行丢弃和慢客户端断开数取所有连接清理完成后的最终指标。

## 4. 结果判定

### 1000 连接：稳定档

1000 个连接全部建立，约 450.9 万次客户端广播接收完成，P99 为 41.55ms，过载、错误、上行丢弃、下行丢弃和慢客户端断开均为 0。按 15 秒配置窗口折算，客户端合计处理约 30 万次广播接收/秒。

### 2000 连接：容量拐点

连接可以全部建立，但连接数达到 2000 后，多数秒的客户端接收量降为 0，P95 和 P99 上升到秒级。服务端开始拒绝上行任务，并因每个连接的有界发送队列积压而断开 1724 个慢客户端。

这说明当前负载模型下，系统的稳定容量拐点位于 1000 到 2000 个连接之间。2000 不能作为“稳定承载”数据。

### 5000 连接：连接建立成功，广播承载失败

5000 个目标连接中建立了 4994 个，但服务端最终断开 4152 个慢客户端，并记录约 194 万次下行广播丢弃。测试配置时长为 18 秒，进程实际耗时 33.07 秒，额外时间主要消耗在过载后的连接清理。

5000 档 P50 低于 2000 档不代表性能更好。大量慢连接被断开、更多广播被丢弃后，延迟样本只剩下成功到达客户端的消息，存在明显的幸存者偏差；此时应优先看 P95/P99、丢弃数和慢客户端断开数。

## 5. 可使用的结论

严谨表述：

> 在 8 核 16GB 单机、1000 个 WebSocket 连接、约 300 条/秒上行的单房间场景下，完成 450.9 万次广播接收，端到端 P50/P95/P99 为 4.80/22.64/41.55ms，错误和广播丢弃均为 0；通过 1000、2000、5000 连接阶梯压测，定位当前负载模型的容量拐点位于 1000 到 2000 连接之间。

不能表述为“系统稳定支持 5000 个高并发连接”。本轮只能证明服务能够建立接近 5000 个套接字，不能在该连接规模下持续完成全房间广播。

## 6. 原始文件

- `1000-valid.log`：1000 连接有效结果；`1000.log` 为修正延迟样本上限前的作废结果。
- `2000.log`：2000 连接结果。
- `5000.log`：5000 连接结果。
- `*-server-resources.log`：服务端进程 CPU 和内存采样。
- `*-metrics*.json`：服务端指标快照。

延迟采用 10 微秒精度、10 秒上限的固定直方图统计全部有效样本，避免仅保留前 100 万条消息造成分位数偏差。
